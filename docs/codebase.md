# Rachit Auth Server Documentation

## Overview

`Rachit Auth` is a custom OpenID Connect / OAuth2 identity provider built with Node.js, Express, PostgreSQL, Prisma, and a React frontend. It is deployed at `auth.rachittaneja.in` and provides secure login, consent, token issuance, and client registration.

It supports:

- OAuth2 authorization code flow with PKCE
- OpenID Connect identity tokens
- browser session login via secure cookies
- client app registration
- consent handling
- refresh tokens
- OIDC discovery and JWKS endpoints

This document explains how the full system works, how the backend and frontend interact, and how key pieces are structured.

## Who this document is for

- Developers who need to understand the architecture, auth flow, and source files
- Reviewers who want a concise functional overview of the service
- Operators who need to know how the app is built and deployed

## What this system does

In plain terms, `Rachit Auth`:

- lets users sign up and sign in with an email/password account
- creates a secure session so users do not need to log in again on every request
- allows apps to register as OAuth clients and request user authorization
- asks users for consent before authorizing a client
- issues temporary authorization codes and exchanges them for tokens
- provides signed JWTs and refresh tokens for client applications
- publishes discovery metadata and signing keys so clients can integrate easily

The auth server is live at `auth.rachittaneja.in`. You can:

- Register OAuth clients and obtain `client_id` and `client_secret`.
- Test the full OIDC flow by logging in and granting consent.
- Inspect the discovery document (`/.well-known/openid-configuration`) and JWKS endpoints (`/.well-known/jwks.json`).
- Use it as a reference for implementing client applications that integrate with this auth server.

## How to run the app

### Prerequisites

- Node.js (v18+)
- PostgreSQL database
- npm or yarn

### Setup

1. Clone the repository and install dependencies:
   ```bash
   npm install
   ```

2. Set up environment variables:
   - Copy `example.env` to `.env`
   - Update the values for your database and deployment

3. Generate RSA keys for JWT signing:
   ```bash
   npm run generate-keys
   ```

4. Set up the database:
   ```bash
   npx prisma migrate dev
   npx prisma generate
   ```

5. Start the server:
   ```bash
   npm run dev
   ```

### Frontend

The backend serves the static frontend from `client/dist` after the build.

To build the frontend:
```bash
npm run build:client
```

To build the full project:
```bash
npm run build
```

### Environment Variables

See `example.env` for required environment variables:

- `DATABASE_URL`: PostgreSQL connection string
- `CLIENT_ORIGIN`: Frontend URL (e.g., `http://localhost:5173`)
- `BASE_URL`: Auth server URL (e.g., `http://localhost:3000`)
- `PORT`: Server port (default 3000)
- `NODE_ENV`: Environment mode
- Optional RSA key variables if not using `certs/` files

## Backend architecture

### `src/app.js`

This file sets up the Express application:

- Enables JSON body parsing using `express.json()`
- Configures CORS:
  - `POST /api/auth/token` and `GET /api/auth/logout` are open endpoints with permissive CORS
  - all other routes require `CLIENT_ORIGIN` and credentials support
- Uses `cookie-parser`
- Mounts three routers:
  - `/api/clients` → client registration and listing
  - `/` → OIDC discovery endpoints
  - `/api/auth` → auth, login, consent, token, logout
- Adds convenience routes:
  - `/ping`
  - `/authorize` redirect wrapper to `/api/auth/authorize`
- Serves SPA static assets from `client/dist`
- Serves `index.html` for non-API routes to support client-side routing
- Uses centralized error handling via `errorHandler`

### `index.js`

Loads environment variables with `dotenv` and starts the Express server on `process.env.PORT || 3000`.

## Authentication routes and flow

### `src/routes/auth.routes.js`

Main auth endpoints:

- `GET /api/auth/me` — returns authenticated user profile
- `GET /api/auth/userinfo` — returns user claims for a valid access token
- `GET /api/auth/authorize` — OIDC authorization endpoint
- `POST /api/auth/signup` — user registration
- `POST /api/auth/login` — user login and auth code redirect
- `POST /api/auth/consent` — user consent handling
- `POST /api/auth/token` — token exchange for auth code or refresh token
- `GET /api/auth/logout` — logout and session cleanup

### `src/controllers/auth.controller.js`

This controller contains the core auth behavior.

#### `authorizeClient(req, res)`

Called when a client app starts the authorization flow.

Steps:

1. Validates `client_id` and registered `redirect_uri`
2. If no session cookie exists, redirect user to the login page with original query params
3. If session exists but is invalid or expired, clear cookie and redirect to login
4. If the user has previously authorized this client, issue an authorization code
5. Otherwise redirect to the consent page

This is the session-aware part of the flow: if the user already has a browser session, the auth server can skip login and continue the OIDC flow.

#### `signupUser(req, res)`

- Registers a new user
- Validates unique email
- Hashes password with `bcrypt`
- Stores user record in PostgreSQL

#### `loginUser(req, res)`

- Validates user credentials
- Creates a `Session` record
- Sets an HTTP-only `sessionId` cookie
- If login is part of an OAuth flow, the response includes a redirect URL:
  - if consent already exists, it generates an auth code and returns a final client redirect URL
  - otherwise redirects to the consent step

#### `submitConsent(req, res)`

- If the user denies consent, returns `access_denied` to the client
- If the user accepts consent:
  - saves a `Consent` record for that user+client
  - issues an authorization code
  - returns redirect URL back to the client app

#### `exchangeToken(req, res)`

Supports two grant types:

- `authorization_code`
  - validates `client_id` and `client_secret`
  - finds and verifies auth code
  - checks PKCE `code_verifier`
  - issues:
    - `id_token` (RS256 JWT)
    - `access_token` (RS256 JWT)
    - `refresh_token`
- `refresh_token`
  - validates refresh token and expiration
  - issues a new access token

#### `logoutUser(req, res)`

- deletes the session
- clears the `sessionId` cookie
- optionally redirects to a registered `post_logout_redirect_uri`

#### `userInfo(req, res)`

- accepts a bearer access token in `Authorization: Bearer <token>`
- validates the access token signature and expiry
- returns public user claims such as `sub`, `email`, and `name`

## OIDC discovery and JWKS

### `src/routes/discovery.routes.js`

Exposes OpenID Connect metadata and public keys.

- `GET /.well-known/openid-configuration`
- `GET /.well-known/jwks.json`

### `src/controllers/discovery.controller.js`

#### `openIdRouter`:

Returns standard OIDC metadata:

- issuer
- authorization endpoint
- token endpoint
- userinfo endpoint (advertised but not implemented)
- end session endpoint
- JWKS URI
- supported response types, scopes, claims, and auth methods

#### `jwksRouter`:

Loads the public key and key metadata and returns a JWKS response for JWT verification.

## Database and data model

### `src/config/db.js`

- Uses Prisma client with PostgreSQL
- Reads `DATABASE_URL` from environment
- Uses `@prisma/adapter-pg` with a `pg` pool

### `prisma/schema.prisma`

Key models:

- `User`
  - stores user account data
  - related to sessions, auth codes, consents, refresh tokens, and clients

- `Client`
  - registered OAuth applications
  - `clientId` and `clientSecretHash`
  - stores `redirectUris`

- `Session`
  - browser session records
  - maps `sessionId` cookie to a user
  - includes expiration

- `AuthCode`
  - authorization codes for OAuth flow
  - stores PKCE `codeChallenge`
  - expires quickly

- `Consent`
  - stores whether a user has granted access to a client
  - prevents repeated consent prompts

- `RefreshToken`
  - long-lived refresh tokens for renewing access tokens
  - supports revocation with `isRevoked`

### Database behavior summary

- `Users` sign in with email/password
- `Clients` are apps that request auth codes and tokens
- `Sessions` allow single sign-on behavior in the browser
- `AuthCodes` are short-lived one-time codes for the authorization code flow
- `Consents` persist authorization decisions
- `RefreshTokens` allow apps to refresh access tokens without user login

## Frontend architecture

The frontend is a React single-page app in `client/src`.

### `client/src/App.jsx`

- Uses `react-router-dom`
- Routes:
  - `/` → `Home`
  - `/register-app` → `RegisterClient`
  - `/login` → `Login`
  - `/signup` → `Signup`
  - `/consent` → `Consent`
  - `/logout` → `Logout`
- Detects auth state by calling `/api/auth/me`
- Renders nav links conditionally based on login status

### `client/src/utils/api.js`

A wrapper around `fetch` that:

- sends JSON requests with `Content-Type: application/json`
- includes credentials for cookies
- parses JSON responses
- throws errors for non-2xx responses

### Login flow

The login page (`Login.jsx`) does this:

- reads all query params from the URL
- posts credentials plus those params to `/api/auth/login`
- the backend returns a `redirectUrl`
- navigates to that URL or reloads the browser if the URL is external

This supports OAuth flow by preserving `client_id`, `redirect_uri`, `response_type`, `state`, `code_challenge`, and `code_challenge_method`.

### Consent flow

The consent page (`Consent.jsx`) shows a prompt and then:

- posts consent decision to `/api/auth/consent`
- includes the original auth query params
- receives a redirect URL and forwards the browser to the client app

### Client registration

The client registration page allows authenticated users to create new OAuth clients. It sends the registration request to `/api/clients/register` and receives a new `client_id` and `client_secret`.

### Logout flow

The logout page calls `/api/auth/logout`, which clears the browser session and optionally redirects to the requesting client.

## How the OIDC + SSO flow works

### 1. Client application starts auth

A client app redirects the browser to `/api/auth/authorize` with:

- `client_id`
- `redirect_uri`
- `response_type=code`
- `scope` (usually `openid` and profile scopes)
- `state`
- `code_challenge`
- `code_challenge_method`

### 2. Auth server checks the session

- If the browser already has a valid `sessionId` cookie, the user is treated as logged in
- If not, the user is redirected to the login page
- This is where SSO-style behavior appears: an existing browser session can satisfy login for multiple clients

### 3. Consent

If the user has not previously granted consent for the client, they are redirected to `/consent`

### 4. Authorization code issuance

After login/consent, the auth server creates an `AuthCode` record and redirects back to the client with `code` and optional `state`.

### 5. Token exchange

The client exchanges the code for tokens at `/api/auth/token` using client credentials and PKCE verifier.

### 6. Tokens

The auth server returns:

- `access_token`
- `id_token`
- `refresh_token`
- `token_type`
- `expires_in`

## Notes and gotchas

### OIDC Compliance and Endpoints
- The discovery document (`/.well-known/openid-configuration`) shows a `userinfo_endpoint` at `/api/auth/userinfo`, which is fully implemented for external clients to retrieve user claims using a bearer access token (e.g., `Authorization: Bearer <access_token>`). This returns standard claims like `sub`, `email`, and `name`.
- The auth server is a custom OIDC provider, not a generic third-party identity federation service (e.g., no built-in Google or Azure AD integration). It focuses on self-hosted user management.

### Session and Authentication
- Sessions are stored server-side in the database and tied to browser cookies (`sessionId`) for login persistence. This enables SSO-like behavior across multiple client apps in the same browser.
- The frontend SPA uses `/api/auth/me` (session-based) for authenticated user profiles, while `/api/auth/userinfo` is strictly for OIDC-compliant token-based access by external applications.

### Security and Best Practices
- Client secrets are hashed in the database using bcrypt and raw secrets are only returned once during registration. Store them securely and never expose in logs.
- PKCE is required for all authorization code flows to prevent code interception attacks.
- JWTs (ID tokens and access tokens) expire quickly: ID tokens in 1 hour, access tokens in 15 minutes. Use refresh tokens for long-term access.
- CORS is configured to allow token endpoints (`/api/auth/token`, `/api/auth/logout`) from any origin for client apps, but other routes require the `CLIENT_ORIGIN` for security.

### Deployment and Configuration
- RSA keys can be loaded from `certs/` files or environment variables (e.g., `PRIVATE_KEY_BASE64`). Generate keys with `npm run generate-keys` before production.
- In production, set `NODE_ENV=production` for secure cookies (`sameSite=none`, `secure=true`).
- The server serves the React SPA statically; ensure `CLIENT_ORIGIN` matches your frontend URL to avoid CORS issues.
- Database migrations must be run with `npx prisma migrate dev` (or `deploy` in production) to keep the schema up-to-date.

### Limitations and Extensions
- No built-in support for advanced OIDC features like dynamic client registration, token introspection, or custom scopes beyond `openid`, `profile`, `email`.
- Userinfo endpoint only returns basic claims; extend it if you need additional profile data.
- Refresh tokens are revocable but not automatically rotated; consider implementing token rotation for enhanced security.
- The system assumes HTTPS in production; ensure your deployment uses SSL to protect cookies and tokens.

If you encounter issues, check the server logs for OIDC-prefixed messages (e.g., `[OIDC Boot]`, `[OIDC JWKS]`) for key loading or JWT errors.
